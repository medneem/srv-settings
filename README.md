# srv-settings

Интерактивный Bash-инструмент для первоначальной настройки и последующего администрирования VPS/серверов Ubuntu.

> **Статус:** проект в разработке. Сейчас опубликована документация; `bootstrap.sh`, `setup.sh` и модули ещё предстоит реализовать. **Команда быстрого запуска пока не работает.**

## Быстрый запуск (после реализации)

Для запуска будет достаточно **одной команды** на сервере Ubuntu:

```bash
curl -fsSLo /tmp/srv-settings-bootstrap.sh https://raw.githubusercontent.com/medneem/srv-settings/main/bootstrap.sh && sudo bash /tmp/srv-settings-bootstrap.sh
```

Стартовый `bootstrap.sh` будет:
1. Проверять Ubuntu, права root и необходимые зависимости.
2. Скачивать/обновлять файлы проекта из этого репозитория.
3. Запускать интерактивное меню `setup.sh`.

Планируемое расположение файлов после установки — `/opt/srv-settings/`. Для повторного запуска меню:

```bash
sudo bash /opt/srv-settings/setup.sh
```

**Почему не `curl | bash`?** Скрипт интерактивный: он спрашивает имя пользователя, пароль, порты и подтверждения. При запуске через pipe стандартный ввод Bash занят самим скриптом. Скачивание в файл и отдельный запуск сохраняют нормальный ввод с терминала. Кроме того, перед выполнением можно посмотреть содержимое скачанного файла.

Для предварительного просмотра:

```bash
curl -fsSLo /tmp/srv-settings-bootstrap.sh https://raw.githubusercontent.com/medneem/srv-settings/main/bootstrap.sh
less /tmp/srv-settings-bootstrap.sh
sudo bash /tmp/srv-settings-bootstrap.sh
```

> Не запускайте команду на рабочем сервере, пока не изучены скрипты, а настройки SSH и firewall не проверены на тестовой VPS. Используйте консоль провайдера/VNC на случай потери SSH-доступа.

## Планируемое главное меню

```text
========== SERVER SETTINGS ==========

1. Полная первоначальная настройка
2. Управление портами TCP/UDP (UFW)
3. Настройка SSH
4. Управление пользователями и sudo
5. Настройка Fail2ban
6. Настройка Docker
7. Обновление системы
8. Диагностика и проверка состояния
9. Резервное копирование конфигурации

0. Выход
=====================================
```

В режиме полной настройки мастер будет последовательно запрашивать:
- имя нового пользователя и пароль (без вывода пароля на экран);
- добавление пользователя в группу `sudo`;
- порт SSH и разрешение/запрет входа по паролю;
- список открытых TCP-портов через запятую, например `80,443,1443`;
- список открытых UDP-портов через запятую, например `26,27,1053`;
- часовой пояс, синхронизацию времени и прочие параметры;
- настройки Fail2ban, включая `maxretry`, `findtime` и `bantime`.

## Планируемые возможности

- **Ubuntu:** первоначально ориентация на Ubuntu Server 22.04 LTS и 24.04 LTS; другие версии — после проверки совместимости.
- **Система:** обновление пакетов, часовой пояс, NTP, базовые утилиты.
- **Пользователи:** создание пользователя, настройка sudo, управление доступом.
- **SSH:** отдельный конфиг в `sshd_config.d`, проверка `sshd -t`, учёт `ssh.socket` в Ubuntu 24.04.
- **UFW:** разрешение/удаление TCP/UDP-портов, просмотр правил, настройки логирования.
- **Fail2ban:** установка, настройка защиты SSH, проверка состояния и разблокировка IP.
- **Docker:** опциональная настройка зеркал реестра с резервной копией существующего `daemon.json`.
- **Диагностика:** состояние SSH, UFW, Fail2ban, прослушиваемые порты и журналы.
- **Повторный запуск:** операции должны быть идемпотентными и не дублировать правила.

## Требования к безопасности

1. Перед изменением SSH сохранять резервную копию конфигурации и проверять её синтаксис.
2. Сначала разрешать новый SSH-порт в UFW, и только потом переключать SSH. Старый порт закрывать **после проверки нового подключения**.
3. При настройке удалённого сервера не полагаться исключительно на существующую SSH-сессию; предусмотреть безопасный откат.
4. Не включать `NOPASSWD: ALL` автоматически: только отдельной опцией и после подтверждения.
5. Для SSH предпочтителен вход по ключу; парольный вход — явный выбор пользователя.
6. Не перезаписывать существующие настройки SSH, UFW или Docker без проверки и резервной копии.
7. Учитывать, что опубликованные Docker-порты могут обходить обычную фильтрацию UFW; правила доступа к контейнерам требуют отдельного внимания.
8. Не сохранять введённые пароли в логах.
